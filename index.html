Voici mon analyse, par ordre de probabilité, puis le code corrigé. Cause la plus probable Un bug de configuration PeerJS : le test local testRelay() passe, mais l'appel réel utilise un autre chemin. Dans PeerJS 1.5.4, peer.call() et c.answer() n'héritent de config que si vous le passez dans le constructeur de Peer, ce que vous faites. Mais PeerJS remplace iceServers par défaut s'il y a une config sans sdpSemantics, et surtout il n'applique pas iceTransportPolicy de manière fiable sur tous les navigateurs mobiles. Le point décisif est ailleurs : Les identifiants ExpressTURN gratuits sont à durée limitée, et vos identifiants sont publiés dans le code (donc publics). Le test testRelay() ne prouve qu'une chose : votre navigateur obtient une allocation. Il ne prouve pas que : l'autre personne, depuis son réseau, atteint free.expressturn.com:3478 en UDP (souvent bloqué sur mobile/Wi-Fi d'entreprise), les deux pairs ont une allocation en même temps (le quota gratuit est très restreint, et les comptes gratuits limitent les allocations simultanées). Avec iceTransportPolicy: 'relay', si un seul des deux côtés ne peut pas joindre le TURN, il n'y a aucun repli : ICE reste en checking puis passe en failed. C'est exactement votre symptôme. Réponses aux questions 1. Pourquoi checking malgré les candidats relay ? Obtenir un candidat relay local ≠ pouvoir échanger des paquets avec l'autre relais. Il faut que les deux allocations existent et que les permissions TURN soient créées (ce qui dépend des candidats de l'autre côté). Si l'un des deux ne passe pas (UDP bloqué, quota, identifiants), les paires restent en checking. 2. Expiration ExpressTURN ? Oui, c'est probable : le bouton « Refresh Credentials » indique que les identifiants sont temporaires. Les identifiants collés en dur finissent par être refusés. Le plan gratuit est aussi limité en bande passante/allocations. TCP sur 3478 fonctionne en principe, mais beaucoup de réseaux mobiles ne laissent passer que 443 : essayez turn:...:443?transport=tcp ou turns: si votre tableau de bord les fournit. 3. PeerJS et appel entrant ? Oui, ça fonctionne : peer.on('call') + answer() utilise la même config. Pas de souci de ce côté. Un vrai problème est cependant la course de rôles : si b appelle pendant que a est encore en reconnexion, l'appel est perdu sans erreur claire. Vos retries gèrent partiellement ça. 4. Solution plus robuste ? Metered.ca (plan gratuit, 50 Go/mois) avec l'API de credentials dynamiques : c'est le plus simple, votre code le gère déjà via TURN_API. À privilégier. Cloudflare Calls/TURN : très fiable, gratuit dans de larges limites, nécessite une petite fonction serveur (Netlify Function) pour générer les credentials. LiveKit Cloud : très robuste, mais plus lourd à intégrer. Copier-coller SDP : fonctionne sans serveur, mais ne résout pas le problème TURN/NAT. Corrections à appliquer Ne plus forcer relay en dur : utiliser all en premier, avec un repli relay. Cela permet le P2P direct quand c'est possible et évite l'échec total. Ajouter les ports 443/TCP et turns: si disponibles. Détecter l'échec et redémarrer l'ICE (restartIce), avec un bouton de diagnostic. Logger les candidats pour savoir quel côté échoue.
